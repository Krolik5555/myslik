# MCP-мост «Мыслик»: что доработать

Составлено 2026-09-07 по итогам живой задачи — «составить план разработки аддона и оформить
в виде нод». Задача сделана (ветка «Аддон с нуля: план разработки», 41 нода), но больше
половины ходов ушло не на план, а на обслуживание форматов моста. Ниже — что именно мешало,
с замерами, и что с этим сделать.

## Состояние: пункты 1–9 сделаны 07.09.2026

Разделы ниже оставлены как есть — в них замеры и ПРИЧИНЫ, по которым сделано именно так; текст
«Сейчас» описывает состояние ДО правок, а не сегодняшнее. Что получилось:

* снимок принимает `graph`, `area`, `root`, `depth`, `limit`, `cursor`, `fields`, `format`
  (`cmdSnapshot(opts)`), печатается без отступов (флаг `tight` у инструмента);
* срез честный: `truncated`/`total`/`returned`/`next_cursor`, обрыв на границе ветки,
  `links` только между отданными нодами;
* правила отделены от снимка — метод `rules`, инструмент `myslik_rules`
  (вместо `myslik_format`, его больше нет);
* `preview` возвращает `token` (одноразовый, три минуты) и `will` — сколько чего появится;
  `apply` принимает `token` вместо пакета и отвечает `created` с именами из пакета;
* `has_body` в снимке; `undo` отвечает числом нод после отката; `ping` и снимок считают
  ноды одинаково (`cmdCounts`).

Проверки на всё это — в `tools/scenarios/команды.js` (`dev.py run команды`).

Прогон КРОЛИКА на живом графе (424 ноды) прошёл целиком; три хвоста из него подчищены тем же днём:

* `depth` работал только вместе с `root`, а с `area` молча ничего не делал — теперь глубина
  считается и от корней выборки (`cmdSnapDepth`/`cmdSnapKids`);
* из правил убрано «из снимка ниже»: в `myslik_rules` никакого «ниже» нет;
* срез рвался на первой же границе ветки (`limit:100` → 56 нод). Граница уважается, только пока
  не съедает больше четверти порции; иначе режем ровно по лимиту — висячих связей это не даёт.

Снимок без аргументов так и весит около 60 КБ: это не дефект, а причина, по которой у него
появились фильтры, и описание инструмента об этом предупреждает прямым текстом.

Правки трогают два файла:

* `planner/ui/js/cmd.js` — вся кухня: `cmdSnapshot()` (497), `cmdPrompt()` (531),
  диспетчер `cmdAgent()` (604), константа `CMD_SNAP_NODES` (23).
* `planner/mcp_server.py` — тонкий прокси: схемы аргументов и описания в `TOOLS` (155),
  обёртки `_t_snapshot` / `_t_format` / `_t_preview` / `_t_apply` (123–144), сериализация
  ответа (222).

Новый метод RPC надо не забыть внести в белый список `planner/app.py:516`.

## Замеры этой сессии

| Что | Объём | Что из этого вышло |
|---|---|---|
| `myslik_format` | 57 171 символ | не влез в лимит ответа, выгружен в файл |

Пять лишних вызовов оболочки ушло на то, чтобы распарсить эти выгрузки питоном и построить
из них дерево — то есть на работу, которую мост мог отдать готовой.

Ориентир по объёму: ответ около 57 КБ хост уже не показывает, а сбрасывает в файл на диск.
Типовой ответ моста надо держать в пределах 10–15 КБ.

## П1 — без этого следующая такая задача снова уедет в файлы

### 1. Снимок с фильтрами и компактным выводом

**Сейчас.** `cmdSnapshot()` отдаёт весь активный граф целиком: все ноды и все связи.
Выбрать ветку или область нельзя. Сверху `mcp_server.py:222` печатает ответ с `indent=1` —
383 ноды превращаются в 4 382 строки, отступы занимают заметную часть объёма.

**Почему больно.** Чтобы дописать одну ветку, нужны правила, список областей и эта ветка —
несколько килобайт. Приезжает семьдесят.

**Сделать.** Параметры у `myslik_snapshot` (и проброс через `cmdAgent`, объект `p` там уже
разбирается):

* `graph` — id графа, по умолчанию активный (сейчас выбора нет вообще);
* `area` — только ноды этой области;
* `root` — id ноды: отдать её саму и всё поддерево по связям;
* `depth` — глубина от корня, по умолчанию без ограничения;
* `format` — `"json"` (как сейчас) или `"compact"`;
* `fields` — какие поля нужны, по умолчанию `id,kind,title,parent,status`.

Компактный формат — одна строка на ноду, разделитель табуляция, дерево читается глазами
без парсера:

```
graph: Мой граф
areas: a_work=Работа, a_addon=Аддоны, a_other=Прочее
nodes: 41 из 424
mtq6i5clhmz7j	task	next	-	Аддон с нуля: план разработки
mtq6i5clfjghm	task	next	mtq6i5clhmz7j	Разобраться, зачем аддон
links: mtq6i5clhmz7j>mtq6i5clfjghm, ...
```

И `indent=1` в `mcp_server.py:222` убрать хотя бы для снимка: отступы здесь ничего не дают,
читает это машина.

**Проверка.** `myslik_snapshot {root: "<id корня ветки>"}` на графе из 424 нод возвращает
только эту ветку и укладывается в 3 КБ.

### 2. Честный срез

**Сейчас.** `CMD_SNAP_NODES = 400`, дальше `.slice(0, 400)` по порядку `S.items`.
О срезе сообщается строкой: `снимок.note = "показаны первые 400 нод из 424"`.
Связи при этом не фильтруются — `links` отдаются целиком, включая рёбра на срезанные ноды.

**Почему больно.** Строка `note` лежит рядом с `nodes` и легко теряется при разборе —
я её пропустил и решил, что в графе 400 нод; расхождение вылезло только при сверке с `ping`.
Срез идёт по порядку хранения, то есть режет произвольные ноды посреди веток, а оставшиеся
связи ссылаются на то, чего в снимке нет.

**Сделать.**

* Машинные поля вместо строки: `truncated: true`, `total: 424`, `returned: 400`
  (строку `note` можно оставить дополнительно, для человека).
* `links` фильтровать по отданным нодам: ребро попадает в снимок, только если обе его ноды
  в нём есть.
* Резать по веткам, а не по индексу: если ветка не помещается целиком, честнее оборвать
  на следующей, чем разорвать эту посередине.
* Курсор для продолжения: `cursor` в запросе и `next_cursor` в ответе, чтобы большой граф
  можно было дочитать.

**Проверка.** На графе из 424 нод `myslik_snapshot {limit: 100}` возвращает `truncated:true`,
`total:424`, и в `links` нет ни одного id, отсутствующего в `nodes`.

### 3. Разделить правила и снимок

**Сейчас.** `myslik_format` = `cmdPrompt()` = правила (~8 КБ, меняются раз в полгода) плюс
полный снимок (~49 КБ) одной строкой. Описание инструмента велит звать его первым перед любой
правкой — то есть каждый раз тянуть весь граф.

**Сделать.** Либо новый метод `rules` и отдельный инструмент `myslik_rules`, либо параметр
`include_snapshot` у `myslik_format` со значением по умолчанию `false`. Новый метод внести
в белый список `planner/app.py:516`. Описание переписать под порядок: правила → узкий снимок
нужной ветки → `preview` → `apply`.

**Проверка.** `myslik_rules` возвращает меньше 10 КБ и не содержит ни одного id ноды.

## П2 — заметно экономит на каждой правке

### 4. `apply` по токену от `preview`

**Сейчас.** Один и тот же пакет уезжает дважды: в `preview` и в `apply`. В этой сессии —
два пакета по ~10 КБ, то есть около 20 КБ на пересылку уже проверенного.

**Сделать.** `preview` возвращает `token` (живёт минуту-другую, привязан к разобранному
пакету), `apply` принимает либо `ops`, либо `token`. Если граф успел измениться — отказать
и попросить повторить `preview`.

**Проверка.** `preview` → `apply {token}` создаёт ровно то же, что `apply {ops}`, при этом
пакет отправлен один раз.

### 5. `created` с именами из пакета

**Сейчас.** `apply` возвращает массив id в порядке создания. Какое `as` какому id
соответствует — приходится угадывать по порядку.

**Сделать.** `created: {"root": "mtq6i5clhmz7j", "e1": "mtq6i5clfjghm", …}`. Ноды без `as` —
под своим id, как сейчас.

**Проверка.** После пакета с `as:"root"` в ответе видно, какой id получил `root`, и на него
можно сразу сослаться следующим пакетом.

### 6. Показывать, что у ноды есть тело

**Сейчас.** Тела и содержимое полей в снимок не идут — это правильно. Но не видно и того,
пустое тело или нет.

**Почему больно.** `edit body` затирает текст целиком. Не зная, есть ли там что-то, дописывать
в существующие ноды опасно: в этой сессии я поэтому обошёл `body` стороной и складывал
пояснения в отдельные поля, хотя тела, скорее всего, были пустые.

**Сделать.** Флаг `has_body: true` (или `body_len: 240`) — без самого текста. Приватность
не страдает: наружу уезжает только факт наличия.

**Проверка.** У ноды с телом в снимке стоит `has_body:true`, у пустой поля нет, самого текста
в снимке не появляется нигде.

### 7. `undo` и `ping` должны отвечать согласованно

**Сейчас.** Наблюдение: после `myslik_undo` (вернул `{ok:true}`) сразу вызванный `ping` показал
409 нод, а `snapshot` следующим вызовом — уже 383, то есть откат к тому моменту прошёл.
Похоже, `undo` отвечает раньше, чем состояние окончательно приведено в порядок.

Плюс `ping` и снимок считают по-разному: `ping` берёт `(S.items||[]).length`, а снимок
фильтрует через `inWeb` — числа расходятся и без всякой гонки.

**Сделать.** `undo` возвращает `{ok:true, nodes:N}` после фактического отката. `ping` и снимок
считают одинаково; если числа принципиально разные, отдавать оба явно (`nodes_total`
и `nodes_in_web`).

**Проверка.** `apply` (41 нода) → `undo` → `ping`: число нод совпадает с тем, что было
до применения, с первого же вызова.

## П3 — комфорт

### 8. Описания инструментов под новый порядок

После правок 1–3 переписать `desc` в `TOOLS` (`mcp_server.py:155`): сначала правила, потом
узкий снимок по ветке или области, и только потом `preview` / `apply`. Сейчас описание
`myslik_format` толкает агента тянуть весь граф первым же ходом.

### 9. Мелочи

* В ответе `preview` возвращать не только число операций, но и сколько появится нод и связей —
  расхождение с задуманным видно до применения.
* `graphs` уже отдаёт число нод по каждому графу, этого хватает: менять не нужно.

## Чего менять НЕ надо

Это работает хорошо, при доработке не сломать:

* Протокол операций (`node` / `link` / `field` / `edit` / `area`) и приём пакета строкой
  или массивом.
* Связка `preview` → `apply` и то, что весь пакет — один шаг истории.
* Требование `allowDelete:true` отдельным полем.
* Отсутствие тел нод и содержимого полей в снимке.
* Тост «ИИ-агент …» с кнопкой «Вернуть»: человек видит, что в планер написали снаружи.
* Правила в `cmdPrompt()` про форму ветки — цепочка для последовательного, веер для
  параллельного, без нумерации в заголовках. Написаны точно, по ним сразу понятно, как строить.

## Проверка 07.09.2026 — работает, три хвоста

Тест-план прогнан целиком на живом графе (424 ноды, «Мой граф»), приложение перезапущено.

| Пункт | Итог |
|---|---|
| 1. `myslik_rules` | ~7 КБ, ни одного id, в конце — как брать id снимком |
| 2. снимок по `root` | ветка из 41 ноды, 4 292 символа в `compact` |
| 3. снимок по `area` | работает и по id (`a_addon`), и по имени («Аддоны») |
| 4. срез | `truncated`/`total`/`returned`/`next_cursor`; связей на ноды вне снимка — 0; продолжение по курсору не пересекается с первой порцией |
| 5. `format:"compact"` | строка на ноду, шапка `cols:`, связи одной строкой |
| 6. `has_body` | есть; ключа `body` в ответе нет нигде |
| 7. `preview` → `apply {token}` | пакет уехал один раз; повтор того же токена отвергнут |
| 8. `created` | словарь «имя из пакета → id» |
| 9. `undo` | сразу отвечает числом нод, без гонки с `ping` |

Дополнительно: `fields` режет поля до заданных; `graph` открывает другой граф по имени; ошибки
разбора приходят с номерами операций, и битый пакет не оставляет следов — после отказа в графе
ровно столько же нод.

Что осталось подчистить:

1. **`depth` действует только вместе с `root`.** С `area` он молча игнорируется: запрос
   `{area:"a_addon", depth:2}` вернул все 64 ноды области. Либо применять глубину к корням
   области, либо честно сказать об этом в описании параметра.
2. **В правилах остался хвост от снимка.** Строка «Ссылаться можно и на настоящий id из снимка
   ниже» в `cmdPrompt()` — снимка ниже больше нет, id берут отдельным вызовом.
3. **Срез недобирает до лимита.** `limit:100` вернул 56 нод, продолжение по курсору — 94.
   Обрыв происходит на первой же границе ветки; если добирать следующие ветки, пока помещаются,
   ответы станут плотнее.

Снимок без аргументов — 60 868 символов (было 70 532 с отступами): по-прежнему уедет в файл.
Это ожидаемо, описание инструмента об этом предупреждает.
